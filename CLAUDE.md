# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

OpenTrustRegion is a Fortran library implementing a second-order trust-region optimizer, exposed via Fortran, C, and Python (ctypes) interfaces — the same compiled shared/static library is consumed by all three. The core solver (`src/`) is agnostic to what is being optimized: it operates purely on abstract parameter/gradient/Hessian-vector-product callbacks. Domain-specific functionality is layered on top as opt-in extensions under `extensions/<name>/`. Three of these, OAO, MO and ARH, are chemistry-specific — they build density-matrix and orbital-optimization machinery on top of the core solver. OAO and MO each provide an orbital object, the orbitals parameterized in the orthogonalized AO basis and in the MO basis; ARH parameterizes the orbitals in either basis, on top of the corresponding extension, so `ENABLE_ARH` always builds OAO and MO. The MO numerics never depend on OAO's: what both bases share lives in `extensions/common` (ARH's C and Python interfaces build on OAO's or MO's for the respective basis). The other two, quasi-Newton and S-GEK are, like the core, agnostic to the underlying problem; they just add alternative Hessian-approximation strategies.

## General conventions

Apply equally to `src/` and every `extensions/<name>/`.

**Formatting.** Fortran lines max 88 columns. Layout, spacing, keyword spelling, string literals, comments and blank lines of Fortran code are defined by `tools/f90_layout.py`, whose docstring is the authoritative rule list; don't restate its rules here or apply them by hand. Run `python3 tools/f90_layout.py` after every Fortran edit: by default it checks only statements touched relative to `HEAD`, `--fix` applies the fixes, and `--all` checks whole files (with `--fix` it requires explicit paths, e.g. `git ls-files '*.f90' | xargs python3 tools/f90_layout.py --all --fix`). CI runs `--all` on every tracked `.f90` file. The default mode also checks every untracked, non-ignored `.f90` file in full, so a bare `--fix` rewrites scratch copies of Fortran files left in the tree too; move them out first. Statements containing a comment, a `;` or a continuation line starting with `&` are never reflowed (their spacing and indentation are still fixed), so shorten an overlong one by hand. Every procedure opens with a `!`-delimited comment block describing what it does; each logical step inside gets a lowercase `!` comment. Unit tests: assume success (`test_<name> = .true.`), then one `if (...) then` / `write(stderr, *) "test_<name> failed: ..."` / `test_<name> = .false.` block per assertion, no early returns except where a later assertion would crash or has nothing to check because a call it depends on already failed.

**Python formatting.** All Python (`pyopentrustregion/`, its `extensions/`, `setup.py`, `tools/`) is `black`-formatted, default settings. Run `black pyopentrustregion setup.py tools` before considering Python changes done.

**C formatting.** All C headers and test sources (`include/`, `tests/*.c`) are `clang-format`-formatted per the repo-root `.clang-format` (LLVM style, 88-column limit to match the Fortran convention above). Run `clang-format -i` on touched C/H files before considering C changes done.

**Clarity over performance.** The library is not on the hot path of a quantum-chemistry calculation — the host program's integral transforms and Hessian-vector products dominate. Prefer short, obviously-correct code over fast code. Don't propose performance refactors (buffer growth, pooling, micro-optimizations) without evidence the affected code is hot for a real workload. This does not extend to the OAO, MO and ARH extensions: they run in every solver iteration and ARH's approximate Hessian replaces the host's exact Hessian-vector products, so their per-iteration work competes with what they replace. Don't add avoidable `O(n^3)` work there for simplicity, such as transforming the same matrix twice or rebuilding a matrix an object already holds.

**Norms: BLAS in production, intrinsics in tests.** Production Fortran (`src/`, `extensions/*/src/`) uses BLAS (`dnrm2`, `ddot`) for norms/dot products. Test code (`tests/`, `extensions/*/tests/`) uses intrinsics (`norm2`, `dot_product`, `matmul`, `sum`, `transpose`) instead. BLAS/LAPACK is allowed in tests only where no intrinsic exists (`dsyev`, `dgeev`, `zheev`) — don't hand-roll linear algebra to avoid the dependency.

### Unit tests must not depend on untested code

A unit test may only call the routine it is testing — never another production routine to build its inputs or expected values, or the test silently inherits that routine's correctness.

- Construct inputs directly in the test, randomly or with LAPACK, not by calling the production routine that would normally produce them.
- When a routine under test internally calls another module's routines, reimplement those as `ref_*` helpers so the expected value is computed independently — e.g. `ref_unpack_asymm` / `ref_pack_asymm` / `ref_project_asymm` / `ref_hess_x_oao` in `extensions/oao/tests/oao_unit_tests.f90`, used by both OAO's and ARH's tests.
- Where a routine merely delegates (e.g. a role callback such as `update_orbs_callback` returning what the object's `update_orbs` produced, or ARH's `precond_pd_arh` what the `precond_pd` of its orbital basis produced), assert the *contract* — that it hands its inputs to the callee and passes on what the callee returned — rather than re-deriving numbers a different routine's own test already covers.
- Exercise only the options the routine itself distinguishes. Where it calls another production routine, its test checks only that the callee was called (with the right arguments, and that its result is used correctly), not the callee's options or the input regimes that drive the callee down different branches; those belong in the callee's own test. E.g. `test_solver` checks that the solver, with `line_search` set, hands the step to `bracket`, while which bracketing branch an objective function takes is covered in `test_bracket`.

### Test code layout

Classify test code by **role** first, then place it at the most common **level** that needs it.

Roles, one file each:

| File | Role |
|---|---|
| `test_reference.f90` | Tolerances, reference values, and `ref_*` reimplementations computed independently of the routine under test. The reference settings `ref_solver_settings`/`ref_stability_settings` are values of the production types with a distinct value in every field but the logicals, which the tests set one at a time instead, and the callbacks and context, which `get_reference_*_values` sets to distinct addresses; C and Python get them field by field without the conversion routines under test, as a filled C struct (`get_reference_solver_values`) or by field name (`reference_field`), so their tests hold no values of their own. The reference states `ref_solver_state`/`ref_stability_state` likewise have a value in every field that is distinct from every other field of the same kind and from its default, exported as a filled C struct (`get_reference_*_state_values`) or by field name (`reference_state_field`); `arm_state_c` lets a callback bundle refer to a state and a host's record holding other values, so that the C mocks detect whether the state was copied into the record before they were called. `same_callbacks`, `unset_callbacks` and `callbacks_wrapped` compare against the callback functions of an expected object, unset or check the wrapping of every callback function of Fortran or C settings, so a new callback function is listed there once instead of in every test; `same_callbacks` also compares C callback bundles, `common_test_reference.f90` extends it to the host records of extension objects, and a test checks that no callback function is set by comparing with an object without any (the default settings, or C settings after `unset_callbacks`), while contexts are checked on their own. The checkers `check_<callback>_funptr`/`check_<callback>_c_funptr`, which the mocks and the `*_f_wrapper` tests use to check the function pointers they receive, sit side by side as Fortran/C pairs for every callback that returns values or an error code; the logger has none and is called directly. Also the host-context fixtures shared by both unit suites: `host_context_type` with its `host_context` instance, `arm_host_context`/`arm_host_context_c`, `check_host_context`/`check_host_context_c` and `host_context_reached`, `host_context_error`, through which the C mocks report an error set in the host context, the `bind(C)` checks `is_default_solver_settings`/`is_default_stability_settings` that the C `*_init()` tests use, the sizes of the `bind(C)` settings and state types, `solver_settings_size`/`stability_settings_size` and `solver_state_size`/`stability_state_size`, that the layout tests compare against, and the warnings the C entry points print for settings that were not initialized, as null-terminated strings for the C integration tests, whose capture of the standard error flushes what the Fortran runtime buffered there through `flush_fortran_stderr`, since it buffers the standard error while that is a file. |
| `<name>_unit_tests.f90` | The Fortran-level `test_*` functions, plus mocks/fixtures needed only to drive them (e.g. a stand-in `evaluate_dm`). |
| `<name>_mock.f90` | Mocks of the module's *own* production routines that are bridged to the C interface (the factories), so a caller (typically `<name>_c_interface_unit_tests.f90`) can verify invocation without running the real logic. |
| `<name>_c_interface_unit_tests.f90` | Tests for the `bind(C)` wrapper layer; defines its own local `bind(C)` mocks rather than using `<name>_c_interface_mock.f90`. |
| `<name>_c_interface_mock.f90` | `bind(C)`-signature mocks used exclusively by the Python interface tests, dynamically loaded via `ctypes` from `libotrtestsuite`. |
| `opentrustregion_system_tests.f90` | The system tests on the water Foster-Boys localization, see below. |
| `c_integration_tests.c`, `<name>_c_integration_tests.c` | The C integration tests through the header of the core or of an extension, see below; what those of the extensions share is in `common_c_integration_tests.c`. What one of these files provides to others is declared in its header (`<name>_c_integration_tests.h`), which the file itself includes, so that the compiler checks the definitions against the declarations its users see, since C links by name only. |

Level: within `tests/`, `extensions/common/tests/`, and a specific extension's `tests/`, code lives at the most common level shared by everything that *actually* needs it — verified against real usage across every extension, not assumed from whichever extension motivated writing it.
- Needed by every extension → `extensions/common/tests/` (e.g. `common_mock.f90`'s `mock_update_orbs`/`mock_hess_x`, since `update_orbs_type`/`hess_x_type` and their C bridge are defined once in the core).
- Needed by some → the most foundational one among them. ARH depends on OAO and MO, so an OAO-specific helper shared between OAO's and ARH's tests (e.g. the `ref_*` twins of OAO's numerics) lives in `oao_unit_tests.f90`, and an MO-specific one shared between MO's and ARH's tests (e.g. `setup_mo_object` or the `ref_*` twins of the MO numerics) in `mo_unit_tests.f90`. OAO and MO do not depend on each other, so anything their tests share (shared dimensions, generators, mock-call recording, the reference value of the shared settings) lives in `common_test_reference.f90`/`common_unit_tests.f90`, and the `bind(C)` mocks of the exact-evaluation callbacks their C-interface tests share in `common_c_interface_unit_tests.f90`, while `common_mock.f90` holds the callback mocks the C-interface tests of every extension need (`mock_update_orbs`, `mock_obj_func`).
- Needed by one → that extension's own files. The mock logger and `setup_settings`, needed by nearly every Fortran-level unit test, live in `tests/opentrustregion_unit_tests.f90`.

This recurses within a role: a helper belongs in `<name>_test_reference.f90` vs `<name>_unit_tests.f90` based on whether something *at that level* calls it — not which extension's tests happen to use it (`ref_unpack_asymm` etc. live in `oao_unit_tests.f90`, since only unit tests call them).

**`ref_*` naming.** The prefix marks a role — an independent reimplementation of what a production routine computes — not a location; it travels with the function wherever the placement rule moves it, and it is decided by what the helper computes, not by whether a call site compares against it or feeds it in as an input. A fixture that builds a *plausible* input (randomly, via LAPACK, or by reassembling a routine's own output) does not take the prefix, even in the same file. Either kind may keep an atypical name purely to dodge a collision with a production routine or local variable in scope at its call site (`ref_unpack_asymm` keeps its prefix because `unpack_asymm` is in scope) — check for a collision before insisting on the "cleaner" name.

**Module-level `use` in test files is restricted.** In `<name>_unit_tests.f90` and siblings, module-level `use` statements above `contains` are limited to `rp`, `ip`, their C counterparts `c_rp` and `c_ip`, `kw_len`, `stderr`, `stdout`, `tol`, `tol_c`, the dimension `n_param`/`n_param_c` and the reference settings `ref_solver_settings`/`ref_stability_settings` (with the operators comparing against them) that `test_reference.f90` fixes for the C-interface fixtures and, in the tests of an extension, its reference settings `ref_<name>_settings` with their operators, and intrinsic module bindings (`iso_c_binding` and the like) — check other modules for the exact set before adding to it. Names from `iso_c_binding` are always imported at module level, never inside a procedure. The exceptions are what a declaration in the module's specification part needs: the parent of a test-local type extension, since a type with type-bound procedures can only be declared there (`common_unit_tests.f90` imports `orbital_basis_type` for its `mock_orbital_basis_type`), the interface of a procedure pointer that checks a mock complies with it (`procedure(update_orbs_c_type), pointer :: mock_update_orbs_ptr => mock_update_orbs`), the type of a variable in which a mock records what it received (`received_stability_callbacks` in `opentrustregion_mock.f90`), the type of a component of a test-local type or of a module-level fixture (`solver_state_type` for `double_well_state_context_type`, the mock states in `opentrustregion_mock.f90`, `armed_state_c` in `test_reference.f90`), and a generic interface the module extends (`same_callbacks` in `common_test_reference.f90`). Everything else (mock callbacks, `setup_settings`, other shared dimension parameters, `ref_*` helpers) is imported locally inside the specific `test_*` function that needs it, even if several functions in the file need the same symbol. A module-level `use` beyond this set pollutes every procedure in the file and hides which test actually relies on what.

**Prefer shared dimension-parameter fixtures over local literals**, unless it complicates the test a lot. The test reference modules define canonical dimensions (`otr_common_test_reference` those both orbital bases use, OAO's and MO's reference modules the derived and MO-specific ones) that most unit tests should import rather than redeclaring. In the core, where a canonical dimension exists for the data a test works on, import it rather than redeclaring it: the core unit tests' `n_param` is the dimension of the Hartmann 6D problem most of them share, defined with that problem in `opentrustregion_unit_tests.f90`, and `test_reference.f90`'s `n_param` is the dimension of the C-interface fixtures.
- Every dimension is defined once, without a basis suffix (`n_ao`, not `n_ao_mo`), and one quantity has one name (the number of occupied orbitals of a channel, which is also the rank of its density matrix, is `n_occ` everywhere, never `n_electrons`).
- A test whose local variable already carries the name renames the import on its `use` line only, with the suffix `_ref` (`n_occ_ref => n_occ`), never the prefix `ref_`, which marks independent reimplementations.
- The shared `n_param` is only right for a test that works at the shared `n_particle`; a test pinning its own `n_particle` (closed-shell-only, or walking both shells in one body) needs its own local value.
- Exception: a test whose expected values are hand-derived for a specific small/structured case (a closed-form 2×2 rotation, 3×3 matrices with hand-computed results, a matrix crafted to trigger a rank-detection path) may keep local literals and declare its own dimensions, since forcing the shared size would mean re-deriving the numbers. When correctness is checked via algebraic properties rather than exact values, use the shared fixture.

**Prefer generated data over hand-typed literals** (`generate_random_density_matrix` / `generate_random_symm_matrix` / `call random_number`), unless the specific values are load-bearing. A hand-typed `reshape([...])` is justified only when the test checks a specific hand-derivable closed-form target depending on those exact numbers (a weighted-symmetrization blend, a dependency-screening path, a regularization threshold crossed at a specific eigenvalue). When every assertion is relational (a copy, a fixed scaling, an algebraic identity, or a value the test recomputes independently from the same input) the specific values never mattered, and random generation exercises the same code path while being harder to accidentally pass with a bug. Before hand-typing a matrix meant to be "just some valid state" (often signaled by the test calling it "arbitrary"), check whether random generation works instead. Where a matrix must stay block-diagonal/diagonal/structurally constrained to match what production produces, keep that structure but randomize within it.

### Shared architectural patterns

**Settings types.** `solver_settings_type` / `stability_settings_type` (core) and each extension's own settings type (`s_gek_settings_type`, `qn_settings_type`, and `oao_settings_type`, `mo_settings_type` and `arh_settings_type`, which extend `otr_common`'s `orbital_settings_type`, the settings the orbital objects hold) all extend the abstract `settings_type`, with an `init` type-bound procedure and an `initialized` flag. `settings_type` also holds the logging function and the host context, and the core's `optimizer_settings_type` between it and the solver and stability settings what both of these share. The core's settings are inputs only: `solver` and `stability_check` take them `intent(in), optional` and work on a local copy (`local_settings`), of the default settings when none are passed, so the caller's settings are never written; only `init`, the default resolution `init_defaults` and the sanity checks write the copy, and every other internal routine takes it `intent(in)`. What the core reports lives in the states (below). The owning routine checks `settings%initialized` on entry (the core's `solver` and `stability_check` that of their copy) and calls `init` if needed, after printing a warning through the caller's logging function, or on stderr without one, regardless of the verbosity, since the defaults `init` sets would silence it; `solver` does the same for its nested `stability_settings` up front, before `init_defaults` lets them inherit the solver's callbacks and context, since the internal stability check's own `init` would discard these. The extensions' factories do the same for their own settings, on a copy, and for the solver settings they wire their routines into and these settings' nested stability settings, which the solver can no longer detect as uninitialized once the routines are wired into them; `warn_uninitialized_settings` prints all of these warnings, and `init_uninitialized_settings` warns about and initializes uninitialized solver settings or their nested settings for both `solver` and the extensions' wiring. Unlike the core's, the conversions of the extensions' C settings leave uninitialized settings uninitialized, and the extensions' C factories warn about and initialize them before pointing their context at the bundle through which the Fortran wrappers of the host callbacks find these, which the Fortran factory's initialization would discard. C/Python wrappers pre-populate defaults via `*_init()`/`__init__` so the flag is `.true.` by the time Fortran sees it. C settings that arrive uninitialized anyway are replaced by the defaults in the core's `assign_*_f_c` conversions rather than left to `init`, which would also discard the callback bundle the C wrapper stores in `settings%context`; as in Fortran, such settings carry no host context, so `store_optional_c_callbacks` skips the optional callbacks and context of uninitialized C settings. Since the conversion leaves the owning routine nothing to detect, the C entry points print the warning themselves: the stability check's on stderr, and the solver's conversion `convert_solver_settings_c` through `warn_uninitialized_settings` on the settings it converted, so on stderr for uninitialized settings, which provide no logging function, and through the solver's logging function, or on stderr without one, for uninitialized nested settings; the C factories of the extensions convert the host's C solver settings through it too (in `setup_extension_holder`), so they print the same warnings, which the Fortran factory, receiving initialized settings, cannot. The C entry points take `const` settings pointers that may be `NULL` and Python `settings=None`, both meaning the defaults; without settings, the C wrappers work on a copy of the default settings (`local_settings_c`) rather than passing none on, since the Fortran settings carry the callback bundle in their context. The extensions' factories take their own settings the same way, optional in Fortran, `NULL` in C and `None` in Python. Default values are defined once in a `default_*_settings` parameter; the C `*_init()` helpers and the Python `Settings` wrappers obtain them by calling `init_*_settings_c` (C name `init_*_settings`) in `src/c_interface.f90`, those of the extensions in `extensions/<name>/src/<name>_c_interface.f90`.

**States.** What the core reports lives in `solver_state_type`/`stability_state_type`, plain records with default initialization and no `bind(C)`, which `solver` and `stability_check` take as an optional `intent(out), target` argument right after the settings and keep current in place through the pointer `current_state` at the caller's record or a local one, so that a host reaching the record through a pointer reads the current values during a callback. The solver's state nests that of its most recent internal stability check as `stability_state`. The internal routines that update the state while calling callbacks take it as a `target` dummy, those that only count calls of a callback a `target` counter. The C interface has `bind(C)` twins ordered by kind (logicals, reals, integers, nested), converted by `assignment(=)`. The C entry points take a state pointer after the settings (`NULL` for none), and the callback bundles refer to the Fortran state and the host's record; `copy_state_to_c` copies the former into the latter in every callback wrapper right before the call into C and when the call returns, also after an error. Python's `SolverState`/`StabilityState` expose the fields of their ctypes structs as read-only properties (`bind_state_fields`). The extensions' factories require the record of the solver state the host also passes to `solver` (a C `NULL` is an error), at which their object's `state` points, for a C host at the holder's Fortran copy of the host's record, which the C factories reset to the default state, as the solver does, since a C host's record need not be defined before, and which `refresh_state` refreshes before every role the object performs. Neither the settings nor the state structs carry a size or version member: a C program is rebuilt against the header of the library it links, like a Fortran program against its modules.

**The host context.** Every callback interface of the core takes `class(*), intent(in), pointer :: context` as its last dummy (`void *context` in C), including `precond_pd`, `get_extra_trial_vectors`, the stability check's `conv_check`, `approx_hess_x` and `stability_hess_x`, and `settings_type` carries a matching `class(*), pointer :: context` component. The library passes `settings%context` at every call site unconditionally — a *pointer* dummy accepts a disassociated actual, which is why no call site branches on `associated`, and why the component must be `pointer` rather than `allocatable` (the internals declare `settings` `intent(in)`, which protects the pointer association but not the target). `init_defaults` lets the nested `stability_settings` of the solver's copy inherit its context when that is unset, together with its preconditioning, projection and logging functions, so the caller's settings never carry an inherited pointer that could dangle on a reused settings object. When the nested context *is* set it wins: the internal check hands it to every callback it calls, including the `hess_x` returned by the solver's `update_orbs` and the inherited `precond`/`project`/`logger`, so a host that sets one must make those callbacks accept it (documented in the README). `test_inherit_solver_callbacks` checks that nested settings without a context or callbacks of their own inherit the solver's and that their own are kept (`inherit_solver_callbacks`, which `init_defaults` and the extensions' wiring share), `test_check_stationary_point` that the nested context reaches the callbacks of the internal stability check, `test_stability_check` that every callback receives `settings%context`, and `test_convert_solver_settings_c` that the nested bundle of the C settings conversion holds the nested settings' own callbacks and context where they were provided and initialized and the solver's otherwise. Every extension object is an `extension_type` of `otr_common`, whose role callbacks, the callbacks the factories wire into the solver settings and return, receive the object's level as context and call the object's type-bound procedure for the role with it, which forwards to the host's callback in the level's host record with the host context where the extension does not provide the role itself. For C hosts the C wrappers of the roles forward the roles an object does not perform straight to the host's C functions, so a callback in the host record, the core's `*_f_wrapper`, is only called by a role an object performs itself by wrapping the host's, so far the orbital update of quasi-Newton and S-GEK, which calls the host's `update_orbs` while the solver is still running the core's `update_orbs_f_wrapper`, so that one is `recursive`; the role callbacks, their forwarding defaults and the C wrappers of the roles are `recursive` too, since extensions wired one after the other into the same settings re-enter them, as are the orbital updates of quasi-Newton and S-GEK, which an object of the same type wired on top re-enters. The extensions' own host callbacks (`evaluate_dm` and the `get_response` it returns, ARH's own `evaluate_dm`, `transport`, `init_hess` and `change_reference`) take the context as their last dummy too (`void *context` in C, a `c_void_p` argument the Python interfaces drop like the core's `CallbackInterface`), and receive the `context` of their extension's settings, which `log` also hands to the logging function, since the settings are where a host configures what their owner calls. ARH builds on an orbital basis object without changing its settings, so the basis's `evaluate_dm` and `get_response` keep receiving the context of the basis's settings and ARH's `evaluate_dm` that of the ARH settings. The extensions' C settings structs end with a `void *context` field like the core's, which Python's structures leave `NULL`. The mocks of these callbacks check the context they receive with `check_host_context`/`check_host_context_c`; the tests of the routines calling them arm it in the settings of the object they call them through (`arm_host_context`), those of the Fortran wrappers in the extension's callback bundle (`arm_host_context_c`). The Fortran unit tests of quasi-Newton and S-GEK check of their numerical routines so far only that every call site hands the host's function the context of their settings and passes its error on, leaving the numerics, which are still work in progress, untested.

**The Python → C → Fortran call chain:** `solver(...)` in `python_interface.py` takes the `SolverSettingsC` ctypes struct a `SolverSettings` object wraps (`NULL` without settings) and the `SolverStateC` struct of a `SolverState` (`NULL` without a state), wraps its Python callbacks with `CFUNCTYPE` per call, and calls into `libopentrustregion`'s C entry point (`src/c_interface.f90`), which collects the C function pointers plus the host's `void*` and, with a state, pointers to the Fortran state and the host's record in a `c_callbacks_type` bundle on the entry point's own stack frame, stores that bundle in `settings%context`, and invokes `standard_solver` (the real `solver`) with Fortran-shaped wrappers that `select type` the bundle back out. **Consequence:** there is no module-level callback state, so solves nest and run concurrently, provided the library is built with `-frecursive` (gfortran) or `-recursive` (Intel), since a nested call re-enters procedures that are still running; without it, a Debug build stops a nested call at its runtime recursion check (`Recursive call to nonrecursive procedure`). The one piece of process-wide state left is the Fortran runtime's random number generator, which `init_rng` reseeds on every `solver`/`stability_check` call, so a nested or concurrent call perturbs the other's random trial vectors, not its correctness. The internal stability check gets a *second* bundle that starts as a copy of the solver's (so inherited callbacks resolve) and is then overridden by whatever `settings_c%stability_settings` provides — a nested bundle whose slot is empty while the Fortran pointer is inherited would call a null procedure pointer. A signature change must keep all layers (Fortran abstract interface → C wrapper + abstract interface → C typedef → Python `CFUNCTYPE` + `Structure`) in lockstep. Python needs no context: `python_interface.py` accepts arbitrary callables, so closures already carry host data. Every extension defines its own extension of `c_callbacks_type` next to the C interfaces of its host callbacks, with a slot for each of these callbacks (`arh_c_callbacks_type`, `qn_c_callbacks_type`, `s_gek_c_callbacks_type`, and `otr_common_c_interface`'s `orbital_c_callbacks_type`, which OAO and MO share together with the C interfaces of `evaluate_dm` and `get_response` and which also holds the `get_response` the latest `evaluate_dm` returned); the conversion of their C settings converts the logging function like the core's, while the factories, their entry points, keep the C logging function, the host callbacks and the host's `void*` of initialized settings in such a bundle, since the settings outlive the factory call, and point the Fortran settings' context at it. Every C factory allocates a holder (`extension_holder_type`) for every call, which holds the bundle (`extension_callbacks`), the Fortran solver settings the Fortran factory wires, which own the object, and the state, is returned as the host's `void *extension` and is freed by `release_extension`, or right away if the factory fails, so the extensions are re-entrant like the core, and the Fortran wrappers of their host callbacks find the bundle through the context they receive. The core's wrappers select a bundle with `class is (c_callbacks_type)`, so that they accept the extensions' bundles too.

**Where to add coverage for a new setting.** As assertions inside the existing unit test for the routine the setting affects (`tests/opentrustregion_unit_tests.f90`, or the analogous `<name>_unit_tests.f90`), not as a new system test — system tests exercise real chemistry data end-to-end, and one per settings combination would explode combinatorially. When a setting can push a routine down a materially different code path (interior vs. boundary-crossing branch in a trust-region solver), exercise both — a check that only hits the "easy" branch (e.g. always starting near a minimum) can pass while a branch reached only near a saddle point stays untested.

**What the system and integration tests cover.** The tests come in three tiers: unit tests run one routine against mocks, integration tests run the real library through one interface's declarations, and system tests run the real library on real data. Each tier checks what it adds, not the scenarios of the tier below. The system tests check numerical behaviour:

The integration tests gain a check only when a new callback, settings or state field, return value or message on the standard error crosses their interface.

### Registering a new Fortran unit test

A `logical(c_bool) function test_<routine>() bind(C)` is only reachable once wired into all four:

1. The source file in the CMake test source list (`OPENTRUSTREGION_TESTS`, inside the matching `if(ENABLE_<EXT>)` block for an extension test, unconditionally for a core test).
2. The `fortran_tests["<ext>_tests"]` name list in `pyopentrustregion/extensions/<ext>/tests.py` (or the core equivalent in `pyopentrustregion/tests.py`), alphabetically ordered, without the `test_` prefix.
3. An `@add_tests class <Ext>Tests` in that file, whose `tests` attribute is that list.
4. The class import in `pyopentrustregion/testsuite.py`.

A name in the Python list with no matching Fortran symbol fails as that test with `AttributeError: dlsym(...): symbol not found` when it runs.

System tests and C integration tests are wired the same way: their source files are in the same CMake list, and their names go into `fortran_tests["opentrustregion_system_tests"]` and `fortran_tests["c_integration_tests"]` in `pyopentrustregion/tests.py`, or for an extension into `fortran_tests["<name>_c_integration_tests"]` in its `tests.py`, whose `<Name>CIntegrationTests` class runs them next to the Python integration tests of `<Name>PyIntegrationTests`.

**Exactly one registered test per production routine** — never `test_<routine>_<case_a>`, `test_<routine>_<case_b>`. Cover multiple configurations (each `arh_type`, closed vs. open shell, each basis) as cases *inside* that one test: loop where setup can be shared, or call a per-case `check_*` helper that is deliberately not `bind(C)` and not registered. Keep the case name in the failure message (`"test_<routine> failed for <case>: ..."`) since the harness only reports the registered name. Worked example: `test_inv_hess_x_arh` — four cases (MO/OAO basis × closed/open shell), one registered entry, driven by its internal procedure `check_inv_hess_x_arh_case`, parameterized over the basis and the shell. Loop only over the configurations the routine itself distinguishes: `inv_hess_x_arh` depends on the ARH type only through the model it inverts, which its test sets up directly, so its test does not loop over the ARH types.

Because a routine's cases live behind one entry, a silently-skipped case is invisible in suite output — have the driving test run every case unconditionally and combine the results without short-circuiting, rather than returning early on the first failure. Write `if (.not. check_case(...)) test_x = .false.`, never `test_x = test_x .and. check_case(...)`: gfortran skips the call in the latter once `test_x` is false in optimized builds, so the remaining cases neither run nor report.

**Check that an error message was printed, not its text.** When the routine under test detects an error itself, assert the error code and, separately, that an error message was printed, with only error messages passed to the logger and the log cleared beforehand (`setup_error_logging` in `opentrustregion_unit_tests.f90`). Since the routine returns right after printing it, a non-empty log can only be that message; don't compare its text. An error a routine merely propagates from a failing callback prints nothing, so there is no message to check. Warnings keep their exact-text comparison: the routine continues after a warning, so other messages can follow it in the same log. Compare against the `*_warning_msg` parameter the production module defines for each warning instead of repeating its text in the test.

**Error propagation is covered by fault injection.** A routine's own test checks the origin it tags on an error at its own callback call sites (`error_hess_x + 1` for a failing Hessian linear transformation it calls) and on an error an internal callee detects in the routine's own arguments (`error_stability_check + 1` for settings the sanity check rejects), not the `if (error /= 0) return` lines that only pass on an error of a failing callback through an internal callee. Those are covered by the fault-injection sweeps in `test_solver` and `test_stability_check`: an unfaulted run counts every callback call in a `hartmann6d_fault_context_type`, then every one of these calls fails in turn and the test checks that the error is reported with the failing callback's origin and that the reported counters still agree with the calls. A new callback gets a `faulty_*` mock and an entry in the fault lists, and a new option that changes which callbacks the solver or stability check calls gets a case in their sweep. An error that only arises inside an internal callee's algorithm is not provoked through the caller, since the inputs that drive the callee there belong in the callee's own test.

**Helper procedures in test files.**
- A `check_*` (or other non-`bind(C)`) helper earns its existence by eliminating real duplication, never merely to keep one case's code out of the registered test's body — five near-identical one-case functions just relocate the duplication; write one function parameterized over the case, or a loop with a shared body.
- A helper that would be called once without arguments, only reading and writing its host's variables, is part of the host's body and stays inline. A single call justifies a separate procedure only for a mock callback, which has to be a procedure, or for a function of its arguments used in an expression, such as a `ref_*` reimplementation.
- A helper only one procedure uses is an internal procedure of that procedure, after its own `contains`, unless it is one of a family of `ref_*` twins whose other members live at module level (`ref_project_symm` next to `ref_project_asymm`). An internal procedure cannot contain another, so helpers calling each other are nested side by side in their common caller. Mocks in the `*_mock.f90` files stay module procedures however many callers they have, since those files exist to export them.
- Mock callbacks, which a test assigns to a procedure pointer, likewise stay module procedures however few callers they have: gfortran implements a pointer to an internal procedure with a trampoline, which on Linux needs an executable stack that glibc ≥ 2.41 refuses to `dlopen`, breaking the ctypes-driven testsuite (macOS uses heap trampolines, so it looks fine locally).
- An internal procedure uses its host's variables and imports directly instead of redeclaring them or taking them as arguments that every call fills with the host's same-named variable. What must stay its own (loop indices, which would otherwise overwrite a host loop calling it, and dummies receiving a slice or a different array) gets a name the host does not use, so that it never masks a host name.
- Helpers used by several procedures sit together near the top of the file, before the first `test_*` function, grouped by role so that each group only uses the ones above it: mocks and their support, then generators of random or structured data, then fixtures that set up objects or collect their state, then `ref_*` reimplementations, then `check_*` helpers. Where a group uses helpers of a group that this order puts after it, as the reference-settings fixtures in `test_reference.f90` use `ref_character_to_c`, the dependency order wins and the used group moves up. Within a group, helpers concerning the same object stay next to each other, in the order of the production code they serve (variants MO before OAO, closed before open shell, deterministic constructors ahead of random generators); `check_*` helpers follow the order of the tests they drive.
- Names follow the role: `generate_random_<what>` for a generator of random data, `<what>_matrix` for a deterministic constructor (`identity_matrix`, `diagonal_matrix`), `setup_<what>` for a fixture that sets up an object.

**Verify a new test actually fails when the routine is broken.** Mutate the routine (flip a sign, swap an index, drop a term), rebuild, confirm the test fails, then restore. Mutate one routine per rebuild, or several at once only when no test runs more than one of them: the unit tests mock callbacks, not internal callees, so a mutated callee also fails its callers' tests and can hide that a caller's own mutation survived. Leave a second between rebuilds, since a rebuild started in the same second as the previous one can skip relinking `libotrtestsuite` and run the old code. Some mutations are legitimately benign for a given input (scaling safeguards, guards on paths the test doesn't reach) — pick a different mutation rather than concluding the test is weak.

**Before finishing:** build with `-DCMAKE_BUILD_TYPE=Debug` (`-Wall -Wextra -fcheck=all`) and run the suite — it catches out-of-bounds accesses release silently tolerates. Because extension test sources are added per-`ENABLE_<EXT>` block, a new shared test module can break configurations you weren't working on — after touching `extensions/common/`, build with each extension enabled alone, plus none at all.

### CMake options that matter

- `INTEGER_SIZE` (`4` or `8`): library integer width. Unset → CMake autodetects, trying 32-bit BLAS/LAPACK first. Output library named `libopentrustregion_32.*` / `_64.*`. `USE_ILP64` (set whenever the BLAS/LAPACK integer size is 8, including autodetection's 64-bit fallback) switches the Fortran kinds `ip` and `c_ip` to 64-bit as a private definition of the library target, which exports `OTR_ILP64` instead to switch the header's `c_int`, so that C programs linking it see the same width without a generic macro leaking into their sources, and remaps BLAS/LAPACK symbols to `_64` variants when `check_fortran_function_exists` finds them.
- `BLAS_LIBRARIES` / `LAPACK_LIBRARIES`: overriding autodetection requires `INTEGER_SIZE` as well — providing the libraries without it is a fatal error. `OpenTrustRegion_HOST_PROVIDES_BLAS` (the host links BLAS/LAPACK) likewise requires `INTEGER_SIZE` and skips building the testsuite.
- `OpenTrustRegion_BUILD_TESTING` (default `ON` when top-level): builds `libotrtestsuite`, which Python loads to drive the Fortran tests.
- `CONDA_BUILD=1` env var: `setup.py` skips the embedded CMake invocation (the conda recipe builds the C library separately).

### Preprocessing and integer kinds

All Fortran sources (core and extensions) compile with `Fortran_PREPROCESS ON`. Integer kind selection and the BLAS/LAPACK 64-bit symbol remap (`ddot=ddot_64`, etc.) happen via `#ifdef USE_ILP64` and `add_compile_definitions` in CMake — never hardcode integer kinds.

BLAS/LAPACK are called through implicit interfaces (`external :: dgemm`), so gfortran infers each dummy argument's kind from the first call site and rejects a later call that disagrees. Both rules below are invisible in the default 32-bit build, where `ip` is `int32` and `1_ip == 1`:

- **Every integer argument to a BLAS/LAPACK routine must be `ip`-kinded** — `1_ip` not `1` for increments/leading dimensions, `size(x, kind=ip)` when passing on a `size()` result. Same for integers passed to project routines with an explicit `integer(ip)` dummy. Locals used as LAPACK arguments must be declared `integer(ip)`.
- **A newly used BLAS/LAPACK symbol must be added to the remap lists in `CMakeLists.txt`** (`add_compile_definitions("name=name_64")`, guarded by `BLAS_64`/`LAPACK_64`) — including test sources (`zheev` reaches the build only via `tests/opentrustregion_system_tests.f90`). A missing entry links the 32-bit-integer symbol from an ILP64 build, corrupting arguments at runtime rather than failing to build.

**Verifying an ILP64 build without an ILP64 BLAS.** Most dev machines only have 32-bit-integer BLAS, so `check_fortran_function_exists("sgemm_64")` fails and the remap is never exercised. Force it by pre-seeding the cache variables and checking the symbols the objects actually reference:

```sh
cc -shared -o /tmp/blas64stub.dylib /tmp/stubs.c   # one empty function per name_64_ symbol
cmake -S . -B /tmp/build_ilp64 -DINTEGER_SIZE=8 \
      -DBLAS_LIBRARIES=/tmp/blas64stub.dylib -DLAPACK_LIBRARIES=/tmp/blas64stub.dylib \
      -DBLAS_64=1 -DLAPACK_64=1 -DENABLE_OAO=ON -DENABLE_ARH=ON -DBUILD_SHARED_LIBS=ON
cmake --build /tmp/build_ilp64
find /tmp/build_ilp64 -name '*.o' | xargs nm -u | awk '{print $NF}' | grep -E '^_?[dz][a-z0-9]+_$'   # must print nothing
```

The check prints every BLAS/LAPACK symbol referenced without the `_64` suffix. On macOS a clean link proves the same, but Linux links shared libraries with undefined symbols, so rely on the check there. Neither verifies numerical behaviour, which needs a real ILP64 BLAS.

### Known gotchas

- **A `size()`/literal-kind mistake in a BLAS call passes the default build and only breaks under `INTEGER_SIZE=8`**, as `Error: Type mismatch between actual argument at (1) and actual argument at (2) (INTEGER(4)/INTEGER(8))` pointing at two unrelated call sites of the same routine — the two that disagree, not the one that's wrong. Fix by making every integer argument `ip`-kinded, not by changing the named site.
- **`gfortran -fsyntax-only -I<moddir>` gives false confidence.** It checks only the pointed-to file against whatever `.mod` files already exist — it doesn't re-verify those `.mod`s. Editing a `type` whose fields are used across modules can leave a stale consumer `.mod` "passing" syntax-only checks while a real build breaks with `Fatal Error: Mismatch in components of derived type '...': expecting 'X', but got 'Y'`. Always confirm interface changes with `cmake --build`, not `-fsyntax-only`.
- **A `build/` directory created by `pip install` can't be rebuilt directly later.** pip's ephemeral `cmake` path gets baked into `build/CMakeCache.txt` (`CMAKE_COMMAND`) and generated Makefile stamp rules. Once pip's temp env is gone, `cmake --build build` fails with `<temp-path>/cmake: No such file or directory`. Diagnose with `grep CMAKE_COMMAND build/CMakeCache.txt`. Fix: re-run `pip install -e .`, or maintain a separate manually-configured build directory with the system `cmake`.
- **The Python driver only finds a development build in `<repo>/build`.** `python_interface.py` searches the conda prefix, then the installed package, then the `pyopentrustregion/` directory, then `<repo>/build` — a manually-configured `build_manual/` is invisible to it, and it silently loads whatever's in `build/` instead. To drive a custom build directory, run from a scratch directory with symlinks named `pyopentrustregion` and `build`:

  ```sh
  mkdir -p /tmp/run && cd /tmp/run
  ln -sfn <repo>/pyopentrustregion pyopentrustregion
  ln -sfn <repo>/build_manual build
  python3 -m pyopentrustregion.testsuite
  ```
- **A drifted test name list fails only where it is looked up.** `add_tests` looks up each `test_*` function when its test runs, so a name in a list whose Fortran test was renamed or removed fails that test with `AttributeError: dlsym(...): symbol not found`. The extension test modules detect a disabled extension on import instead, the common one through `test_n_ao` of the shared test reference and every other through the `init_<name>_settings` the class body of its settings binds, and `testsuite` wraps each extension's test import in `try/except AttributeError`. Keep the name lists and the Fortran `test_*` functions in exact sync.

## Core library

### Source layout

- `src/opentrustregion.f90` — the numerical core: `solver`, `stability_check`, the Davidson/Jacobi-Davidson/truncated-CG/GLTR subsystem solvers, settings derived types, callback abstract interfaces, error-code constants. Single module, several thousand lines.
- `src/c_interface.f90` — `bind(C)` wrapper module. Collects the C callback pointers in a per-call `c_callbacks_type` bundle held on the entry point's stack and passed through as the opaque context, and adapts C-style `(*)` arrays + return-code functions into Fortran-style `(:)` arrays + `intent(out) :: error` subroutines. `convert_solver_settings_c` converts C solver settings and stores their callbacks and contexts in the bundles of the solver and of its internal stability check, for the solver's entry point and for the holder setup the extensions' C factories share (`setup_extension_holder`). Also holds the `bind(C)` twins of the states and `copy_state_to_c`, which copies the state into the host's record before every callback into C and when the call returns. The module-scope `solver`/`stability_check` procedure pointers remain as test-injection seams; only the wrappers' unit tests point them at mocks, restoring them afterwards, and nothing sets them per call.
- `include/opentrustregion.h` — C header mirroring `solver_settings_type` / `stability_settings_type` and `solver_state_type` / `stability_state_type` as C structs, plus `*_init()` helpers and `solver`/`stability_check` prototypes, whose `const` settings pointers may be `NULL` for the defaults and whose state pointers may be `NULL` for none.
- `pyopentrustregion/python_interface.py` — ctypes wrapper. `SolverSettings`/`StabilitySettings` wrapper classes around the `SolverSettingsC`/`StabilitySettingsC` `ctypes.Structure` mirrors of the C structs, read-only `SolverState`/`StabilityState` classes around `SolverStateC`/`StabilityStateC`, Python callbacks wrapped with `CFUNCTYPE`, integer error codes converted to `RuntimeError`. Every settings object, the extensions' included, builds one `CFUNCTYPE` callback per callback field once, at construction, which calls the callable currently assigned to the field with the `n_param` and exception collector `prepare_call` handed it for the current call and ignores the context, so assigning a callable writes the C settings once and they stay as stable between calls as a C host's (`bind_callback_fields` generates the properties); reading a field returns the assigned callable while the C settings hold the field's own callback, otherwise a Python interface to the C function a factory wired (`CFunctionInterface` and its subclasses), called with the settings' context and keeping the settings alive. These interfaces, like the functions a factory returns, hand the library the arrays they are given in place where it can read and write them, as writeable, C-contiguous `float64` arrays, and C-contiguous `float64` copies otherwise, whose outputs they write back (`c_buffer`, `write_back`).
- `tests/` — `opentrustregion_unit_tests.f90` / `c_interface_unit_tests.f90` (Fortran/C interface unit tests, both in `libotrtestsuite`), `opentrustregion_system_tests.f90` (system tests against `pyopentrustregion/test_data/`), `c_integration_tests.c` (integration tests of the real library through the C header) with `c_integration_tests.h`, which declares the capture of the standard error and the warnings the integration tests of the extensions use too, `opentrustregion_mock.f90` (mocks of `solver`/`stability_check` for the C-interface unit tests), `c_interface_mock.f90` (`bind(C)` mocks for the Python interface unit tests), `test_reference.f90` (tolerances, reference values and shared fixtures). The C and Python integration tests read the Hartmann 6D problem from the `hartmann6d_*` `bind(C)` data that `opentrustregion_unit_tests.f90` exports.

### Fortran/C/Python interfaces must stay consistent

The same callback signatures, settings and state fields, and defaults are described in seven places that must agree — any change to a callback signature or a settings or state field (add/remove/reorder) must land in all seven in the same PR (a state field in all but item 5, since a state's defaults are the default initialization of its type), while a default value changes only in its definition (item 5) and has to stay distinct from its reference value (item 7), except for the logicals:

1. Fortran abstract interfaces, `solver_settings_type`/`stability_settings_type` and `solver_state_type`/`stability_state_type` in `src/opentrustregion.f90`.
2. ### Error codes

Encoded as `OOEE` integers (origin × 100 + specific code, see README). The Fortran core uses `add_error_origin` to tag a non-zero callback error with its origin (e.g. `error_update_orbs = 1200`). Every extension has its own origin (`error_mo = 5100`, `error_oao`, `error_arh`, `error_qn`, `error_s_gek`, in `otr_common`): its factory tags the errors it detects (rejected arguments, refused solver settings, in C a missing record of the state) right after the call that returned them, and its object, through the `error_origin` component of `extension_type`, which the factory or `init` sets and which is 0 for an object a test builds by hand, the errors it detects itself while performing a role, where they are detected or right after the free function that returned them. Nothing is tagged after a call that can return an error of a host's callback function, which keeps the origin of the role, since `add_error_origin` tags only codes below 100 and leaves tagged ones unchanged. An error the numerics of an orbital basis object detect during a role of an ARH object built on it therefore carries the origin of the orbital basis. C entry points return the integer directly; Python wrappers raise a `RuntimeError` that includes the raw code as-is — they don't decode it into origin/specific parts, so callers must read the README table themselves. New origins: add those of the core as a parameter in `opentrustregion.f90` and those of an extension in `otr_common`, and keep the README table in sync.

## Extensions

Opt-in, default OFF (`ENABLE_OAO`, `ENABLE_MO`, `ENABLE_ARH`, `ENABLE_QUASI_NEWTON`, `ENABLE_S_GEK`). `ENABLE_ARH` forces `ENABLE_OAO ON` and `ENABLE_MO ON` in `CMakeLists.txt`. ### Extensions repeat the core's six-location interface pattern

Each extension (`arh`, `mo`, `oao`, `quasi_newton`, `s_gek`) has its own interface chain — a callback signature change touches all six:

1. Abstract interface + settings type in `extensions/<name>/src/<name>.f90` (the exact-evaluation interfaces every orbital basis shares in `extensions/common/src/common.f90`).
2. `bind(C)` interface, slot of the extension's callback bundle type and wrapper in `extensions/<name>/src/<name>_c_interface.f90` (the shared ones of the orbital bases in `extensions/common/src/common_c_interface.f90`).
3. C typedef/struct in `extensions/<name>/include/opentrustregion_<name>.h` (the exact-evaluation typedefs every orbital basis shares in `extensions/common/include/opentrustregion_common.h`).
4. `CFUNCTYPE`/`Structure` in `pyopentrustregion/extensions/<name>/python_interface.py` (the shared ones in `pyopentrustregion/extensions/common/python_interface.py`).
5. Mock callbacks in `extensions/<name>/tests/<name>_unit_tests.f90` and, `bind(C)`, in `<name>_c_interface_unit_tests.f90` (the shared ones of the orbital bases in `extensions/common/tests/common_unit_tests.f90` and `common_c_interface_unit_tests.f90`), with their checkers `check_<callback>_funptr`/`check_<callback>_c_funptr` in `<name>_test_reference.f90`.
6. Reference values in `extensions/<name>/tests/<name>_test_reference.f90` and the Python mock in `pyopentrustregion/extensions/<name>/tests.py`.

A settings field of an extension also needs its value in `ref_<name>_settings`, its comparisons, export and lookup in `<name>_test_reference.f90` and its `check_settings_field`/`check_settings_keyword` line in `test_<name>_settings_layout` in `<name>_c_integration_tests.c`, since C cannot enumerate the fields of a struct; the Python layout test loops over the ctypes fields and needs no change.

A callback signature change also reaches the argument lists and snippets of the README and, for the orbital bases and ARH, the host callbacks of the integration tests (`common_c_integration_tests.c`, and `toy_model`/`ToyRun` in `pyopentrustregion/extensions/common/tests.py`).

If an extension doesn't actually need a given callback, remove it from all six rather than leaving it defined-but-unused — a present-but-ignored parameter looks load-bearing to callers, which will build and pass a closure for nothing.

When a factory-style C interface must accept either of two distinct callback signatures for the same slot (e.g. two shells whose callbacks take different arguments), expose it as a named union of the two typedefs with members named for the two cases, not a generic `void*` or a single opaque typedef — keeps the header type-safe while giving the factory one parameter slot. Where the two signatures coincide, as the closed- and open-shell `evaluate_dm` of the ARH extension do, a single typedef serves both.

### OAO, MO and ARH

The chemistry-specific extensions: OAO builds orthogonal-atomic-orbital machinery on density matrices; MO holds the orbitals parameterized by the occupied-virtual rotations of MO coefficients, with exact-Hessian callbacks like OAO's; ARH (augmented Roothaan-Hall) is a history-based approximate-Hessian method in either the OAO or the MO basis. Quasi-Newton and S-GEK have no equivalent chemistry-specific state — the conventions below don't apply to them.

**Naming.**
- `_cs`/`_os` for closed-shell/open-shell variants, consistently in Fortran, C, and Python (not `_closed_shell`/`_open_shell` or rank-based `_2d`/`_3d`).
- When two routines, types, variables or tests do the same thing in the two orbital bases, both carry the basis after the base name and before the spin and role suffixes: `<name>_<basis>_<spin>_<role>` (`test_construct_arh_mo`, `history_columns_arh_oao`). Implementations of the `orbital_basis_type` methods are `<method>_oao`/`<method>_mo`, those of the ARH methods `<method>_arh_oao`/`<method>_arh_mo`. The `oao_*` prefix of `otr_oao`'s own routines (`oao_factory`, `oao_sanity_check`) is a namespace, not a basis qualifier.
- The roles an extension object provides are its type-bound procedures, `<role>_<extension>` (`update_orbs_oao`, `obj_func_arh`, `project_arh_oao`), tested by `test_<role>_<extension>`; the factories wire into the solver settings and return the role callbacks of `otr_common` (`<role>_callback`), which reach the object through the level they receive as context, and whose interface-checking procedure pointers are `<role>_callback_ptr`.

**Ordering.** Routines, tests, mocks, declarations and C/Python entry points: variants of one routine stay next to each other, MO before OAO (MO is the default basis), closed shell before open shell, and a variant with a role suffix after those without (`mo_factory_cs`, `mo_factory_os`, `mo_factory_common`, `arh_factory_cs`, ...); tests follow the order of the routines they test.

**Factories read the same in all languages.** `mo_factory` and `oao_factory` exist under these names in Fortran, C and Python, with the same arguments in the same order, the sizes included even where Python could infer them from the array shapes — as generics over the two shells in Fortran and one function each in C and Python. `arh_factory`, which builds on the orbital basis object the solver settings were last wired with and therefore takes no orbitals, is one function in C and Python, where the shell comes from that object, and the two specific factories `arh_factory_cs` and `arh_factory_os` in Fortran, since a generic cannot tell apart two specifics that differ only in the interface of a procedure argument; both and the C factory share `arh_factory_common`, which takes the level of the orbital basis object, which the Fortran factories find through the context of the settings and the C factory through the holder level the C settings' context is trusted to be.

**Python checks only what the C interface cannot.** The C interface passes bare pointers, so the Python factories check the array shapes against the sizes, the length of the occupation list (ctypes pads a short one with zeros), the memory layout (a density matrix the factory updates in place must be a writeable, contiguous `float64` array; MO coefficients must be a writeable real array) and that `evaluate_dm` can be called with the positional arguments the factory's callback interface passes, which `check_callback_arguments` (`pyopentrustregion/extensions/common/python_interface.py`) checks through `inspect.signature(...).bind`, so that defaulted and variadic arguments are accepted. MO coefficients are passed through a column-major `float64` buffer (`check_mo_coeff`, `pyopentrustregion/extensions/mo/python_interface.py`): the caller's array itself if it is stored like that, and otherwise a copy, which the owner of the MO object keeps and copies back after every orbital update, also of an ARH object built on it. The Python ARH factory refuses solver settings whose owner is no `OrbitalOwner`, since it takes the dimensions of the orbitals from it. Value ranges (`n_particle` being 1 or 2, a positive `n_ao`, occupations fitting into the MOs) are checked only by the Fortran sanity checks and tested only in their tests, never again in Python.

**Testing the orbital objects.** Tests build the objects they test as local variables, populated directly from test-local `target` arrays rather than by calling the factory (which would violate the no-untested-dependencies rule and drag in the whole setup chain), through the fixtures `setup_mo_object` and `setup_minimal_mo_object` or the ARH ones (`setup_arh_and_mo_objects`, ...), which take the objects as arguments, and `setup_basis_solver_settings`, which lets solver settings own a hand-built orbital basis object as its factory would, for the tests of the ARH factories. Setting `s_inv_sqrt` to the identity makes the AO and OAO bases coincide, removing the basis transformation from expected values. Call the `orbital_basis_type` methods on the object directly, and build ARH objects from the structure constructors (`arh_mo_type(mo)`, `arh_oao_type(oao)`) only after the object's quantities are allocated, since the constructors associate only allocated ones, and only on an orbital object with the `target` attribute that outlives the ARH object. A test's `mo_type` holds its density matrix in `own_dm_ao` and points `dm_ao` at it, as the factory does (`setup_mo_object`).

**Orbital bases and ARH.** The quantities and operations every orbital basis has are components and type-bound procedures of `otr_common`'s abstract `orbital_basis_type`, an `extension_type` whose roles are therefore type-bound procedures too: the settings, the staleness flags and the exact-evaluation callbacks it holds, deferred procedures every basis implements, and shared procedures built on those (`refresh_response`, `fill_extra_trial_vectors`, and the roles `precond` and `precond_pd`), which the procedures of every basis and ARH call instead of repeating them. It is extended by `oao_type` (`otr_oao`) and `mo_type` (`otr_mo`). ARH is the abstract `arh_type`, an `extension_type` as well, holding its own settings, the history, the approximate Hessian model and `orbitals`, a pointer at the orbital basis object the solver settings were wired with when the ARH factory ran, which they own like the ARH object, so that it outlives the ARH object; `arh_mo_type`/`arh_oao_type` extend it with the ARH-only operations, and the factory creates the one of the basis of that object. ARH objects are `class(arh_type)`, so shared code in `otr_arh` dispatches automatically and never branches on the basis, and ARH's numerics (the model builders, `rebuild_stale_hess_model`, `inv_hess_x_arh`, `get_low_rank_hess_factors`, `density_in_history`) are type-bound procedures working on the object they are called on. The ARH types cannot extend `oao_type`/`mo_type` instead, since the history state would have no common ancestor to dispatch on and an orbital basis object with its exact callbacks can serve both its own factory's functions and ARH.
- Methods read the dimensions from `self` and write their own components; a component a method writes is never also passed as an argument, which would alias it with `self`.
- `dm_ao` is a pointer: OAO points it at the caller's density matrix, which it updates in place, while `mo_type` points it at the density matrix it holds itself (`own_dm_ao`). No object frees memory through a pointer, so that the deep copy an assignment of wired solver settings makes of their objects, which the copy never runs, since its context points at the original's, frees nothing twice. Since an `mo_type` points into itself, an assigned copy's `dm_ao` would still point at the original's density matrix, so MO objects are set up where they live and moved with `move_alloc`, as the factory and the wiring do, never assigned.
- The C factories hand the objects the host's density matrix or MO coefficients in place, or a copy where the real kind differs from C's, whose copy-back the holder level of the object holds (see the source layout above), so every C factory returns the shared C wrapper of the orbital update.
- The exact density matrix evaluating function of the orbital basis factories is optional (a disassociated pointer, `NULL`, `None`), for an object only ARH builds on without the exact Hessian for the internal stability check, which the README advises against; the roles that need it check it (`check_evaluate_dm`) and return an error without it, and the factory warns (`evaluate_dm_missing_warning_msg`).
- In the MO basis, the objects provide no projection, so that the wired settings forward to a caller's projection (e.g. a symmetry projection), consistently in Fortran, C and Python; solver settings still carrying OAO's projection are a usage error, which is not detected. In the OAO basis, the objects provide the projection (`project_oao`, `project_arh_oao`), which replaces a caller's.
- Symmetry in the MO basis is the optional last argument `orbsym` of `mo_factory`, the irreps of the MOs of every channel, which ARH in the MO basis takes over from the MO object, in Fortran, C (`NULL` if absent) and Python (`None`). Every `mo_channel_type` stores its `irreps` and the `param_mask` of its same-irrep occupied-virtual pairs (all true without symmetry), and every packing of parameters goes through `pack_ov`/`unpack_ov`/`mo_param_rows`, never through `reshape` or `n_occ * n_virt` counts, so that symmetry needs no other code path; `count_mo_params` counts the parameters also where no MO object holds them, in the sanity check and the factory. `diagonalize_per_irrep` diagonalizes the Fock blocks per irrep and stores every eigenvector at the orbitals of its irrep, so that rotations into the eigenbasis keep the mask pattern and degenerate eigenvalues of different irreps cannot mix them. The MO tests cover symmetry through the shared occupation cases (`case_irreps`); their `ref_*` helpers derive the same-irrep pairs from the channels' irreps, never from `param_mask`.
- The MO history is stored in the AO basis (the MO basis changes every update), densities as `S D S` so that they transform to the MO basis like the potentials (`C^T M C`). Its history columns must stay the *full* `n_mo x n_mo` difference matrices, not their occupied-virtual blocks: differences a finite step apart have second-order oo/vv blocks the potentials respond to, and an ov-only history converged several times slower. Only the packed columns (the parameter space) are ov blocks.

**Every factory call creates a new object.** The orbital basis factories set up a new OAO or MO object for the orbitals they are given, and the ARH factory a new ARH object, with an empty history, on the orbital basis object the solver settings were last wired with, so leftover history from an unrelated trajectory can never survive. Settings wired by an orbital basis object and then by ARH hold the role callbacks of the ARH object, whose host records hold those of the orbital basis object, so the roles both provide are ARH's, while the functions the orbital basis factory returned keep reaching the orbital basis object through the context the settings had right after that factory. All Fortran factories run their sanity checks before they create their object, and an object whose setup or wiring failed is freed without changing the settings.

**Evaluation staleness is an explicit flag, never inferred from values.** The orbital updating callbacks evaluate without an orbital rotation only when `evaluation_stale` (in the orbital objects also `response_stale`) is set: it starts `.true.`, is set before the density is rotated and cleared only once the rotated density has been evaluated, so a failed evaluation leaves it set, and ARH adds the current point to its history only while it is clear. The orbital objects' `response_stale` likewise starts `.true.` and is set again whenever `rotate_orbitals` moves the orbitals without rebuilding the response (as ARH does), which makes the exact Hessian refresh the response first. Don't reintroduce proxies such as a vanishing energy or unallocated arrays, which can be legitimate states, and don't give other components default initializers to serve as such markers.
